# Inventory metadata and export compatibility

SQLite schema version 2 adds `inventory_meetings`, so a selected meeting can have a known date, venue, title and source link before its transcript is available. This is inventory evidence, not transcript availability or a model estimate.

Each row has the composite key `(receipt_id, meeting_id)`. `receipt_id` joins `inventory_receipts`, which records the collection run, original response hash, page, retrieval time and locator. The row retains normalized date/title/body/locators, the source's `has_transcript` claim, source status and normalization version. `meeting_id` need not occur in `meetings`: that table continues to identify stored transcript records. Repeated inventories retain separate provenance; they do not create new transcript observations.

Normalization uses original, hash-verified inventory bytes from a run whose date-level coverage is `inventory_complete`. All pages, totals, identities and continuation flags must agree. The selection checkpoint filters identities; its normalized values must exactly match the originals. Partial and failed inventories retain their original receipts but produce no normalized rows. Reserved dates are rejected before any original-file read; the 37 reserved identifiers remain excluded.

Public exports use the latest validated inventory metadata only for coverage-only meetings. A removed meeting can retain its last known metadata while showing `no_longer_listed`. Stored meetings continue to use metadata bound to their current transcript revision. Missing dates/venues remain null when no validated normalized inventory exists. The public field allowlist is unchanged; no transcript text, private annotations or new stance fields are published.

New private bundles include `inventory_meetings.csv`, its column definitions and joins in `dictionary.json`, and `warehouse_schema: 2` in the research manifest. Existing CSV columns retain their meanings. Import this new table as historical inventory observations, not one row per meeting; choose the receipt/run relevant to an analysis before joining to coverage.

The working database migrates additively from SQLite `user_version=1` to `2`. The warehouse family identifier remains `un.transcript-warehouse.v1`. Existing source revisions, raw bytes, coverage and predictions are unchanged. Historical sealed databases are never migrated during verification or replay. Export dispatch reads their SQLite version: version 1 reproduces the original file set and bytes, while version 2 includes inventory metadata. Unknown versions fail closed.

Migration does not synthesize rows from an unbound checkpoint or rewrite older snapshots. Existing meetings gain normalized inventory provenance on their next successful complete inventory. The daily selected frame and weekly reconciliation continue to control those refreshes. Recovery tooling must support schema 2 to resume a schema-2 working database; older application code deliberately rejects it. Restoring a retained schema-1 snapshot remains possible with the compatible reader, without rewriting historical files.

Validation includes synthetic missing transcripts, original-page bindings, late metadata revisions, removal, partial pagination, reserved dates, tampered receipts, unchanged stored-source metadata, additive migration, and exact old-export byte compatibility. Real old-snapshot replay and new publication/replay evidence are recorded in [the operational checkpoint](OVERNIGHT_WORK.md); code publication alone does not establish those outcomes.
